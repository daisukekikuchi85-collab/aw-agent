# Gijiroku (議事録作成)

「見たら分かる」議事録を作るためのスキル。**読むのではなく、見る**ことを前提に設計する。

## 設計思想

このスキルは3つの原則に立つ:

1. **決定とTODOは冒頭に集約** — 開いて3秒で「何が決まった/誰が何をする」が見える
2. **議論は構造で見せる** — 時系列でだらだら書かず、議題ごとに「論点→決定→TODO」のパターンで再構成
3. **発言録ではなく議事録** — 一字一句の書き起こしではなく、結論と理由を抽出する。生の発言が必要な場合は別添として参照可能にする

迷ったら「会議に出ていない人が30秒スクロールして要点を掴めるか?」を判定基準にする。

## 必ず守る出力構造

以下の順序を**変えない**。ユーザーが特に指定しない限り、この骨組みで出力する。

```
# [会議名]

## サマリー
- **日時** / **場所** / **参加者** / **ファシリテーター** / **書記**
- **会議の目的**(1〜2行)

## 決定事項
表形式:#・決定内容・補足

## TODO
表形式:#・タスク・担当・期限・備考

## 議題ごとの議論
### 議題1: [タイトル]
- **背景・論点**
- **議論の要旨**(箇条書き or 比較表、発言は誰の発言か明記)
- **決定**:太字で明示
- **TODO**:あれば

### 議題2: ...

## 保留・次回持ち越し
箇条書きまたは表

## 次回
- **日時** / **アジェンダ案**

## 参考・添付
- 発言録(全文)、共有資料、関連リンク
```

**絵文字は一切使わない。**セクション識別は見出しの言葉だけで行う。

## 議題の再構成のしかた(最重要)

文字起こしは時系列だが、議事録は**論点ごと**に並べ替える。これがこのスキルの肝。

**やること:**
- 文字起こしを読みながら、話題が変わったところを境界として切る
- 切った塊それぞれに「これは何の議題か」というタイトルをつける
- 同じ議題が会議の前半と後半で再登場していたら**一つにマージ**する
- 議題内では「背景 → 論点 → 議論の要旨 → 決定 → TODO」の順に並べる(時系列ではない)
- **議論の要旨では「誰の発言か」を必ず明記する**(例: 「田中:〜という意見」「山田:〜と反対」)。文字起こしで発話者ラベルが付いている場合はそれを使い、付いていない場合はユーザーに確認する

**やらないこと:**
- 「Aさんが〜と言いました。Bさんが〜と返しました」のような時系列の発言羅列
- 雑談や脱線の網羅
- 「〜について話し合った」だけの中身のない記述

**例(悪い)**:
> 田中さんが予算について発言。山田さんが反対。佐藤さんが折衷案を提案。最終的にXに決定。

**例(良い)**:
> ### 議題3: Q4予算の配分
> - **論点**: マーケ予算をペイドサーチからコンテンツ制作に振り替えるか
> - **議論の要旨**:
>   - 田中(賛成):CPA悪化、コンテンツのLTV高い
>   - 山田(反対):短期売上に効くのはペイド
>   - 佐藤(折衷案):段階移行で2ヶ月様子見
> - **決定**: 佐藤案を採用。**11月から月¥500k分を段階的にコンテンツに移管**
> - **TODO**: 田中が移管計画を11/5までに策定

発言者を明記することで、「誰がどの立場だったか」が後から振り返れるようになる。ただし「Aさんがこう言ってBさんがこう返した」のような会話の往復をそのまま残すのではなく、**意見ごとに整理して発言者をタグ付けする**のがコツ。

## 表の使いどころ

提案書スタイルの「比較表」を積極的に使う。以下のときは表にする:

- **選択肢が2つ以上ある**(案A/案B、見積り比較、ツール比較など)
- **担当×期限のように2軸ある情報**(TODOは常に表)
- **数字を並べる**(金額・件数・スコアなど)
- **メリット/デメリットの対比**

逆に**散文で書くべきもの**:
- 背景説明や合意に至った理由(1〜3行のプロセ)
- 1項目しかない情報

## 装飾ルール

提案書サンプルの抑制された装飾感を踏襲する:

- **太字**: 決定内容、担当者名、金額、期限など「目で拾うべきもの」のみ
- **見出し**: H1=会議名のみ / H2=セクション / H3=議題 / H4以下は基本使わない
- **絵文字**: 一切使わない
- **区切り線(`---`)**: 議題と議題の間など、視覚的な切れ目が必要なときだけ
- **色**: Markdownでは基本使わない。.docxでは決定事項とTODOのセル背景に薄い色を入れる程度

「**やりすぎない**」が原則。提案書サンプルが品があるのは、装飾を絞っているから。

## 入力の扱い

ユーザーは以下のいずれかを渡してくる:

1. **文字起こしファイル**(.txt/.vtt/.srt/.md/.docx) — `inbox/` フォルダ（またはオーナーが指定したパス）から読む
2. **チャットに貼り付けたテキスト**
3. **会議の概要だけ伝えられて「整理して」と言われる** — その場合は質問で情報を引き出す

vttやsrtの場合はタイムスタンプを落とし、発話者ラベルだけ残して処理する。発話者が不明な場合は推測せず「発言者A」などプレースホルダーにして、最後にユーザーに確認する。

## 出力の作り方

ユーザーが特に指定しない限り、**Markdown(.md)と Word(.docx)の両方を生成**する。

### Markdown(.md)の生成
- Obsidian で開かれることを想定して、YAML frontmatter は付けない(または最小限)
- 画像埋め込みはしない(ユーザー設定により Obsidian Sync のストレージを節約)
- ファイル名: `議事録_[会議名]_YYYY-MM-DD.md`

### Word(.docx)の生成
- docxスキル（document-skills の docx）を読んでから作る
- 決定事項・TODO のセル背景に淡い色を使う
- ファイル名: `議事録_[会議名]_YYYY-MM-DD.docx`

両方とも `outputs/` フォルダに保存し、保存したパスをオーナーに伝える。

## ユーザーに確認すること

文字起こしを受け取ったら、すぐに作成に入る前に最低限以下を確認(分かっているものはスキップ):

- **会議名**(タイトル) — 不明なら推測案を提示
- **日時** — 文字起こしから読み取れなければ聞く
- **参加者の役割や所属** — 文中で曖昧な場合
- **特に重視したい議題があるか** — 全体均等で良いか、特定議題を厚めにするか

これらが揃ったら、確認なしで一気に生成する。**「下書きを作ります」→ 待たせる、はしない**。一回で完成形を出して、修正があれば後から対応する。

## 言語の扱い

- 日本語の会議 → 日本語で出力(デフォルト)
- 英語の会議 → 英語で出力
- 混合言語の会議 → 主言語で出力し、固有名詞は原語のまま残す
- ユーザーが言語を指定したらそれに従う

## アンチパターン(やってはいけないこと)

- ❌ 文字起こしの単純な要約(時系列のまま短くしただけ)
- ❌ 「〜について議論した」だけの中身ゼロの記述
- ❌ 決定事項とTODOが本文に埋もれている(必ずセクション冒頭に集約)
- ❌ 発言者の感想や雑談を律儀に記録する
- ❌ 確認できない情報を推測で埋める(分からないものは「[要確認]」と明記)
- ❌ TODOに担当者や期限が抜けている(抜けていたら最後に「TODOで担当/期限未確定の項目」として明示)
- ❌ 絵文字を使う(セクションマーカーであっても使わない)
- ❌ 議論の要旨で発言者名が抜けている(誰の発言かを必ずタグ付ける)

## 完成チェック

出力前に自問する:

1. このページを30秒スクロールしたら、決定とTODOが頭に入るか?
2. 「結局何が決まったの?」「誰がいつまでに何するの?」に即答できるか?
3. 装飾を盛りすぎて品が損なわれていないか?
4. 発言の羅列になっていないか?論点で再構成されているか?

3つ以上クリアできていればOK。
